# 개발 전 단계의 변경 대응 구조 제안

이 문서는 합의 전 조사와 선택지의 이력이다. 아래의 대기 상태는 당시 기록이며, 현재 확정 계약은 [요구사항](requirement.md)과 [설계](architecture.md), 구현 결과는 [Task 문서](tasks.md)를 따른다.

- 단계: 읽기 전용 조사와 설계 자문을 반영한 제안 초안. Q1–Q4 확정, Q5 조건부 B 선호, Q6 지원 범위 답변 대기.
- 근거: [검토 목표 R1–R7과 사용자 질문](requirement.md).
- 제안: 기존 8단계에 공통 변경 처리 절차를 적용하고, 과거 실행·현재 기준·현재 수용 여부를 구분한다.
- 이번 변경: 문서 제안만 작성했다. 스킬·DAG 도구·installer는 수정하지 않았다.
- 확정된 정책: 영향받은 진행 작업은 안전한 지점에서 보류·재계획, 미지정 신규 요청은 진행 중 작업을 유지하며 같은 우선순위로 재계산. 기존 완료 이력 보존·후속 Task 추가(Q3), 선언된 기준 불일치의 도구 검사·새 배정 제한(Q4)도 확정했다. 사용자는 독립 세션 조정(Q5)에 B를 선호하되 비용이 크면 A를 선택했다. 아래 제한된 B와 세부 기술 선택은 아직 제안이며 승인된 구현 계약이 아니다.

## 핵심 구조

| 정보 | 필요한 의미 | 보관 위치 제안 |
| --- | --- | --- |
| 변경 기록 `C1` | 원인·사용자 요청/발견 근거·이전/새 기준·영향/미확인 범위·결정·종결 근거 | 최초로 영향받는 단계 문서. 다른 문서는 C ID로 연결 |
| 의미상 개정 `R1@2`, `D1@3` | 요구·설계 항목의 현재 계약과 개정 이유 | requirement/architecture의 해당 ID 항목 |
| 실행 이력 | 어떤 Task가 어느 기준으로 실행됐고 무엇을 관찰했는가 | tasks와 연결된 실행·검증 근거 |
| 현재 수용 판단 | 과거 결과가 새 기준에서도 사용 가능 / 재확인 필요 / 대체됨 | 현재 요구/수용 기준과 Task·검증의 연결 |
| 계획 개정과 담당 | 어떤 계획을 기준으로 후보를 만들고 누가 통합하는가 | tasks의 계획 개정, 각 세션의 `.gsp-work` |

추적 관계와 실행 의존성은 구별한다. 요구·설계·테스트 사이의 참조는 서로 왕복할 수 있지만, 실행 순서를 나타내는 Task DAG에는 순환을 허용하지 않는다. 테스트 실패가 요구 재검토를 유발해도 과거 DAG에 역방향 의존선을 넣지 않고 새로운 검토·수정 실행을 추가한다.

파일 해시는 정확한 소스 상태·오래된 제출물 판별에 사용한다. 요구사항 문서의 공백이나 표현만 바뀌었다고 모든 구현을 무효화하지 않는다. 의미 변경 여부와 개정 범위는 agent가 근거와 함께 판정한다. 사람과 도구 모두 알아야 하는 정보만 항목별로 둔다.

## 공통 변경 처리

1. **변경 포착:** 새 요청, 실패한 검사, 인터페이스 변경, 환경·예산 제약, 담당자 이동 등을 C ID로 기록한다. 일상적인 편집마다 별도 변경 절차를 강제하지 않는다.
2. **현재 기준 확보:** 관련 문서 개정·실제 코드 상태·진행 중 Task·담당자·받은 기준을 확인한다. 오래된 대화 요약만으로 현재 상태를 단정하지 않는다.
3. **영향 후보 조사:** 요구→설계→코드/인터페이스→Task→테스트/리뷰 관계에서 후보를 찾고 실제 소비자·호환성을 확인한다. 관계가 누락됐으면 미확인 범위를 남긴다.
4. **결정:** 이미 합의된 범위의 구현 선택·명확한 결함 수정은 담당자가 처리한다. 새로운 목표·필수 범위·수용 기준·예산 선택은 사용자에게 질문한다. 영향 없는 작업은 계속한다.
5. **기준과 계획 갱신:** 관련 개정과 새 수정/재검증 Task를 기록한다. 현재 수용 조건과 pending 소비자·통합 Task의 의존성도 갱신한다. 변경과 무관한 ID·이력은 유지한다.
6. **검사와 실행:** 포맷·참조·개정·DAG·상태·충돌을 검사하고 필요한 단계만 재리뷰한다. 최신 상태를 바탕으로 다음 작업을 배정한다.
7. **종결:** 현재 수용 조건에 맞는 실제 검증 근거가 모였을 때 변경을 종결한다. 과거 성공과 새 기준의 성공을 구분한다. 문제 시 보류·대안·되돌림을 새로운 변경으로 기록한다.

영향 없음도 이유를 남긴다. 예를 들어 공개 인터페이스와 출력 의미가 동일하고 관련 회귀 검증이 통과했다면 그 경계 밖의 작업을 다시 수행할 필요가 없다. 미확인 연결을 영향 없음으로 취급하지 않는다.

## 수정 범위 결정

| 변경 | 기본 처리 범위 | 재사용할 수 있는 것 |
| --- | --- | --- |
| 오탈자·표현·링크 정리 | 해당 문서의 형식·링크 확인 | 의미가 같은 계약과 검증 결과 |
| 계약을 유지한 내부 구현 수정 | 영향받는 구현·테스트·개발 리뷰 | 해당 요구사항·설계의 유효한 부분 |
| 아키텍처·인터페이스 변경 | 해당 설계·소비자·Task·테스트·리뷰 | 변하지 않은 요구와 독립 컴포넌트 |
| 기대 동작·수용 기준 변경 | 해당 요구부터 연결된 설계·작업·검증까지 | 새 기준과 무관한 기존 결과 |
| 테스트 실패 | 결함·환경 문제·잘못되거나 모호한 기대값 구분 후 해당 범위 | 실패와 무관한 검증 |
| 새 작업 | 기존 목표와 관계·우선순위·의존성을 정리하고 추가 | 진행 중 작업과 완료 이력 |
| 담당자·자원 변경 | 소유권 인계·실제 가용량·계획·배정 갱신 | 검증 기준이 변하지 않은 결과 |
| 취소·보류 | 하위 필수 의무·통합 조건까지 정리 | 이력과 재사용 가능한 후보 |

변경 이름만으로 등급을 고정하지 않는다. 작은 코드 수정이 공개 동작을 바꾸면 요구/설계 수준으로 다시 판단한다. 취소를 `done`으로 표시하지 않는다. 이미 발생한 외부 효과를 되돌리는 일은 별도의 검증 가능한 작업이다.

## 완료 이력과 현재 수용

현재 v1 도구는 running/done의 모든 선행 작업이 done인지 검사한다. 완료한 상위 Task만 pending으로 되돌리면 과거 하위 done과 모순될 수 있다. 따라서 다음을 추천한다.

- 기존 `T1`, `T2`와 당시 done/PASS·기준은 보존한다.
- 새 기준에 필요한 작업을 사용하지 않은 새 ID로 추가하고 이전 작업과의 관계를 기록한다. 예: T7은 T1의 수정, T8은 T2의 새 기준 재검증. 기존 ID를 일괄 재번호하지 않는다.
- `done`은 해당 실행이 당시 계약으로 완료됐다는 사실이다. 현재 수용 여부는 관련 요구/설계 개정과 비교해 별도로 판단한다.
- 기존 결과가 재사용 가능하면 재구현 대신 영향 확인·회귀·재수용 작업만 추가한다.
- 새 Task 추가만으로 끝내지 않는다. **현재 필수 수용 조건과 후속 소비자·통합 조건이 새 실행/검증 결과를 참조하도록 연결한다.** 이미 끝난 통합은 이력으로 남기고 새 기준의 통합 확인을 추가한다.

예를 들어 R1@1을 만족한 T1/T2가 끝난 뒤 R1@2가 생겼다면, T1/T2의 성공은 그대로 남는다. 새 R1@2는 T7/T8과 새 통합 확인이 끝나기 전까지 미충족이다. 관련 없는 R2의 기존 결과는 근거가 유지되면 재사용한다.

계획 개정 번호는 오래된 변경 제출을 찾는 기준이지 모든 Task를 무효화하는 신호가 아니다. 각 Task의 유효성은 그 작업이 실제 의존한 R/D 항목의 개정으로 판단해야 한다.

## 동시 작업과 안전한 반영

- 정본 문서와 현재 수용 상태는 한 통합 담당자가 갱신한다. worker는 받은 기준과 자신의 변경분을 돌려준다.
- 제출물에는 기준 개정·관련 파일 상태·후보 변경·실제 검증 상태를 붙인다. 통합 직전에 현재 기준과 다시 비교한다.
- 기준이 달라졌으면 영향이 없는지 검토하거나 재기반화·재검증한다. 예전 기준 결과를 곧바로 현재 통합 완료로 삼지 않는다.
- 여러 문서의 갱신 도중에는 영향받는 범위가 변경 처리 중임을 표시한다. 관련 문서·DAG 검사가 끝나기 전에 그 범위의 새 배정을 확정하지 않는다. 확인된 독립 범위는 계속 진행한다.
- “읽음”, “변경 적용함”, “그 상태에서 검증함”을 서로 다른 확인으로 기록한다. 진행 중 작업의 보류 시점은 Q1 답변에 따른다.

이는 협력 규칙이다. `.gsp-work` 확인이나 파일 해시 비교만으로 자동 알림·원자적 다중 파일 갱신·배타적 잠금이 생기지 않는다. 실제 동시 쓰기 문제가 확인되면 통합 갱신 구간의 잠금/원자적 교체를 검토한다. Q5 답변에 따라 로컬 조정 프로세스를 선택 기능으로 검토하되, 도입 여부만으로 배타적 쓰기나 즉시 보류를 보장하지 않는다. 접근 불가·담당 불명·중간 상태는 명시적 보류 사유로 남긴다.

## 조정 기능과 비용 검토

사용자는 B(자동 알림·보류 요청·응답 추적)를 선호하되 비용이 크면 A(작업 경계의 공통 기준 확인)를 원한다. 현재 근거로는 기존 Codex 연결을 재사용하는 제한된 B가 후보이며, 모든 독립 프로세스를 지원하는 B의 저비용 구현은 입증되지 않았다.

### 확인한 지원 범위

읽기 전용 `explore` agent(Luna/medium)가 설치된 `/home/minjae/.local/bin/codex`의 도움말과 임시 생성 프로토콜 스키마를 조사했다. 버전은 `codex-cli 0.166.0`이다.

| 근거 | 확인한 기능 | 한계 |
| --- | --- | --- |
| `codex --help`, `codex agents --help` | 공유 로컬 app-server daemon의 세션 탐색 경로 | 실제 세션 목록은 조회하지 않았다. `--no-daemon`으로 실행한 별도 프로세스까지 제어한다는 근거는 없음 |
| `codex queue --help` | thread ID/정확한 세션 이름을 지정한 메시지 큐, 선택적인 resume | 메시지 송신·resume은 실행하지 않음. 전달됐다는 사실이 작업자의 안전한 보류를 뜻하지 않음 |
| `codex app-server --help` | stdio, Unix socket, WebSocket 연결과 스키마 생성 | 서버 시작·설정 변경·외부 연결은 실행하지 않음 |
| `codex app-server generate-json-schema --out /tmp/codex-appschema-q5 --experimental` | thread 목록/시작/재개, turn 시작/steer/interrupt, 수명주기 notification의 스키마 | 임시 메타데이터 생성만 실행. 실행 중 thread 재참여는 해당 서버가 관리하는 thread를 전제. 변경별 업무 ACK는 별도 설계 필요 |

[공식 App Server 문서](https://learn.chatgpt.com/docs/app-server)는 진행 중 turn에 `expectedTurnId`를 지정한 steer, interrupt 요청과 종료 상태, thread/turn 이벤트를 설명한다. 로컬 스키마와 함께 연결 수단의 존재를 뒷받침하며, 이 프로젝트에서 전달·재연결·안전한 보류가 실제 성공했다는 증거는 아니다.

### 제한된 B 제안

- A의 시작/단계 전환/통합 시 현재 기준 확인은 항상 유지한다. B가 꺼져도 이 절차와 기존 기록을 사용할 수 있게 한다.
- B는 같은 PC에서 접근 가능한 공유 Codex app-server와 이 프로젝트에 명시적으로 등록한 thread만 대상으로 한다. 발견한 모든 세션에 메시지를 보내거나, 임의 프로세스·다른 도구·다른 PC를 자동 연결하지 않는다.
- 작은 로컬 Python 프로세스가 게시 완료한 변경 ID·개정과 대상 Task를 확인하고 해당 세션에 통보한다. 파일 저장마다 LLM에 판단을 시키지 않으며, 의미/영향 판단은 기존 주 agent가 맡는다. 변경/대상/개정별 중복 전달 방지와 재시작 복구가 필요하다.
- 작업자 응답은 **전달됨 / 읽음 / 결과 보존 후 안전하게 보류함 / 새 기준 적용·검증함**을 구분한다. RPC 성공이나 turn 종료만으로 뒤 상태를 대신하지 않는다. 무응답은 보류 완료가 아니다.
- Q1에 따라 정상 경로는 안전한 지점의 보류 요청이다. 강제 interrupt를 안전한 저장 완료로 취급하지 않는다. 보류 확인 전 관련 새 배정·통합은 제한하고, 독립 작업은 유지한다.
- 연결이 끊기면 요청과 미확인 상태를 보존한다. A로 운영을 이어가더라도 보류 요청이 해결됐다고 표시하지 않으며, 영향 범위의 현재 기준·안전 상태를 확인해야 통합할 수 있다.
- 대기 중 agent를 자동으로 깨워 새 모델 turn을 시작할지, 확인은 다음 작업 경계까지 미룰지는 지원 범위(Q6) 다음의 비용/정책 결정이다. 기본값을 확정한 것으로 기록하지 않는다.

### 일반 사용자 VM과 추가 설치 제약

사용자는 할당받은 VM에서 일반 사용자 권한으로 개발하며, 별도 프로그램을 설치하지 않고 이용 가능한 수준인지 질문했다. **같은 VM·같은 계정에서 호환되는 Codex와 Python이 이미 제공된다면, 추가 패키지 설치 없이 구현할 경로가 있다.** 이는 구현 가능성 판단이며 현재 B가 완성됐거나 대상 VM에서 실행됐다는 의미가 아니다.

- 기존 A의 문서 확인은 추가 서비스가 필요 없다. 현재 DAG 도구는 Python 3.9+ 표준 라이브러리만 사용한다. 대상 VM에 Python이 없으면 DAG 자동 검사까지 무설치로 제공한다고 주장할 수 없다.
- B의 조정 스크립트는 pack에 동봉하고 기존 Python으로 실행하는 방안을 제안한다. `sudo`, `apt`, `pip`, 별도 DB·컨테이너·시스템 서비스 등록을 필수로 하지 않는다. 파일 감시도 별도 감시 패키지 없이 구현하는 방향이다.
- 설치된 Codex의 `codex app-server proxy --help`는 실행 중인 app-server 제어 소켓에 stdio를 중계하며 `--sock` 경로를 받을 수 있다고 설명한다. Python의 `subprocess`·`json`으로 기존 Codex 중계를 사용할 수 있다는 설계 근거다. 실제 중계 연결은 시험하지 않았다.
- [공식 문서의 Protocol](https://learn.chatgpt.com/docs/app-server#protocol)은 stdio를 JSONL, Unix 소켓 연결을 HTTP Upgrade를 사용하는 WebSocket으로 구분한다. Unix 소켓에 JSON 줄만 직접 쓰면 된다고 가정하지 않는다. 추가 WebSocket 패키지가 필요 없는 기존 Codex 중계 경로를 우선 검증하며, 중계 프레이밍·서버 공유·재접속은 실험에서 확인해야 한다.
- 사용자 소유 경로의 기록/소켓에 접근하고 로컬 사용자 프로세스를 실행할 수 있어야 한다. 일반 사용자 프로세스로 구성하면 관리자 권한은 설계상 불필요하지만, VM 운영 정책이 프로세스나 소켓을 제한하면 B를 사용할 수 없다. 시스템 서비스 이름으로 등록하거나 VM 전체 설정을 바꾸지 않는다.
- B는 설치 없는 실행을 목표로 하지만, 실행 중인 조정 프로세스 자체는 필요하다. 터미널·세션·VM 종료 뒤에도 계속 동작한다고 보장하지 않는다. 프로세스가 종료되면 기록을 보존하고 A의 확인 절차를 사용한다.
- agent별 VM 또는 계정이 다르면 같은 `.gsp-work`와 제어 소켓을 쓸 수 있다고 가정하지 않는다. A도 공통 저장소/전달 수단이 있어야 세션 간 조정이 가능하다. VM 간 자동 연결·인증·외부 포트 구성은 이번 제한된 B의 범위 밖이다.

현재 조사 환경에는 Python 3.13.14와 Codex CLI 0.166.0이 있지만, 사용자 대상 VM의 설치 목록은 확인하지 않았다. 조건이 없으면 자동 설치·업그레이드하지 않고 사용 불가 이유와 A로 가능한 범위를 표시하는 방향이다. B의 실제 연결·권한·재시작 검증은 NOT_RUN이다.

### 비용 구분과 검증 조건

| 항목 | 제한된 B의 예상 부담 | 근거와 미확인 사항 |
| --- | --- | --- |
| 로컬 감시·큐·재전송 | 모델 호출 없이 수행하도록 설계 가능 | Python의 파일/상태 처리로 설계. CPU/메모리/지연은 아직 미측정 |
| 별도 서비스 요금 | 현재 PC와 기존 Codex 연결을 쓰면 신규 유료 서버·DB는 설계상 불필요 | 기존 Codex 사용 비용이나 구독 한도가 없어지는 것은 아님 |
| 변경 해석·응답·재계획 | 추가 모델 사용량 발생 가능 | 영향받는 세션만 통보하고 변경을 묶어 줄일 수 있음. 실제 토큰·요금·소요 시간은 미측정 |
| 구현·유지 | A보다 큼. 연결 관리·중복 방지·ACK·재시작 복구·CLI 버전 대응 필요 | 모든 도구·별도 프로세스까지 지원하면 범위 확대. 현재 일정/금액 추정은 없음 |

따라서 상시 LLM 감시나 범용 세션 제어를 만들기보다 **A를 공통 기반으로 유지하고, 지원되는 Codex 세션에만 B를 추가**하는 안을 추천한다. 저비용이 검증됐다는 결론은 아니다. Q6에서 제한을 수용한 뒤 작은 연결 실험의 범위·모델 사용 한도와 성공 조건을 정해야 한다. 등록한 두 세션의 변경 전달, 안전 지점 보류 응답, 중복/재시작/오프라인 처리, 영향 없는 작업 유지, 실제 추가 사용량을 확인하는 실험이 후보이며 모두 NOT_RUN이다. 과도한 개별 연결 개발이나 새 유료 서비스가 필요하면 사용자 조건에 따라 첫 구현은 A로 한정한다.

## 도구의 역할과 도입 순서

| 담당 | 역할 |
| --- | --- |
| 주 agent | 변경 의미와 영향 조사, 사용자 질문, 문서·Task 갱신, 실제 배정·통합 |
| reviewer | 영향 누락·과도한 재작업·이전 근거의 잘못된 재사용·새 수용 조건 검토 |
| Python | 선언된 ID/참조/개정 일관성, 허용 상태 전이, 영향 후보 전파, 배정 전 구조·제약 검사 |

추천 도입 순서:

1. **공통 절차와 기록 계약:** AGENTS에는 짧은 연결 지침, 각 스킬에는 자기 단계에서 변경을 분류·반영하는 책임을 둔다. 기존 Markdown 정본에 C ID·의미 개정·영향·현재 수용 판단을 기록한다. 이 단계의 자동 검사는 기존 v1 DAG 범위에 한정한다.
2. **가벼운 영향/최신성 검사:** 실제 변경 사례로 필요한 최소 필드를 확인한 뒤 도구를 확장한다. `impact`는 영향 후보와 누락 참조를, `check`는 현재 기준/증거 연결을 점검하도록 고려한다. 아직 구현된 명령은 아니다.
3. **DAG v2와 배정 연결:** 새 기준의 검증이 필요한 작업, 오래된 기준의 후보, 취소/대체 관계를 명시적으로 표현하고 route에 연결한다. 기존 v1은 계속 읽거나 명시적 변환 경로를 제공한다. 현재 strict v1 JSON에는 새 필드를 임의로 넣지 않는다.

schema v2를 도입한다면 실행 상태와 현재 유효성 필드를 섞지 않는 것이 핵심이다. 자동 검사도 실제 의미나 증거의 진실성을 대신하지 않으며, 미확인 범위는 주 agent의 조사·리뷰로 해소한다. 영향 판단이 필요 없는 작은 변경에 모든 장치를 강제하지 않는다.

| 설계 문서의 오탈자만 수정 | 의미 개정·전체 재검증 불필요, 해당 형식 확인 |
| 공유 인터페이스 변경 | 소비자 후보 조사, 영향/미확인 경계 표시, 새 기준 검증 전 관련 통합 제한 |
| 독립 기능 추가 | 관련 없는 진행 작업 유지, Q2 정책에 따른 신규 배정 |
| agent가 옛 기준의 패치를 제출 | 기준 차이 탐지, 검토·재검증 후 통합 |

| 일부 추적 관계 누락 | 영향 없음 판정 대신 미확인 범위와 조사 작업 표시 |

| 작업 취소 | done으로 위장하지 않고 하위 필수 작업·현재 수용 조건 재검토 |
| 문서 갱신 중 중단 | 영향 범위 변경 중 상태 유지, 확인 전 새 배정/완료 주장 방지 |

## 미결정과 검토 한계

[사용자 결정](requirement.md#사용자-결정)에서 Q1–Q4는 추천안/A로 확정했다. Q5는 비용 조건부 B 선호이며 Q6 지원 범위는 미응답이다. 이 문서는 대안을 비교한 제안이며 최종 설계 합의나 구현 준비 완료 판정은 아니다. grilling 라운드를 이어가며 합의 확인 전 구현하지 않는다.

읽기 전용 architect(Sol/high)가 현재 DAG·세션 계약을 확인하고 최소 확장을 자문했다. 이는 native gsp-reviewer의 독립 stage 리뷰 PASS가 아니다. 코드 구현·실행 실험·성능·동시 갱신 실증은 수행하지 않았다. 답변 후 요구를 확정하고 필요한 독립 리뷰를 거쳐 구체 설계로 이어갈 수 있다.
