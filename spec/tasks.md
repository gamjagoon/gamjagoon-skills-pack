## 원문과 범위

사용자의 선행 상황:

> 지금 구조에서 poc를 빠르게 보려고 개발을 했는데 최적화가 필요한 부분이 있어서 다른 agent에게 최적화 구현을 시켰는데 이런경우 작업을 어떻게 시켜야 할까?

현재 요청:

> 오케이 그럼 이렇게 작업이 가능하도록 AGENTS.md 부터 각 agents, skills 까지 한번 더 검토해줘

합의된 맥락은 PoC 담당자가 전체 통합을 책임지고, 별도 에이전트가 격리된 작업 공간에서 최적화를 맡으며, 하나의 `.gsp-work`를 통해 작업 내용과 검증 결과를 공유하는 것이다. HTML 자동 출력 제거와 기존 변경 보존도 유지한다.

이번 작업은 기존 지침의 검토와 확인된 누락 보완이다. 실제 사용자 PoC 코드 최적화, 신규 에이전트 역할, 자동 통신 서비스, 다른 프로젝트 설치, 원격 전송, commit/push는 범위 밖이다. 새로운 제품 요구사항·설계·작업 계획을 작성하는 단계는 시작하지 않았다. 따라서 앞선 세 단계 문서와 리뷰를 새로 만들지 않고, 이 문서에 검토 기준·수정·검증을 기록한다. 기존 8단계 워크플로 자체는 유지한다.

사용자 지정 기한은 없다. 추가 유료 서비스나 인프라를 사용하지 않는다. 모델 호출의 실제 금액은 미확인이다. 신규 성능 PoC는 수행하지 않으며, 문서 시나리오 검토와 로컬 설치 검증으로 이번 범위를 확인한다.

실제 사용자 PoC 성능 개선과 독립 Codex 세션의 자율 동작은 NOT_RUN이다. 이번 PASS는 지침의 정적 시나리오 검증이며 해당 실행을 보증하지 않는다.

## 사용과 한계

1. PoC 담당자가 부모 작업과 baseline, 계약, 최적화 지표·측정 방법, 수정 범위를 전달한다.
2. 최적화 담당자는 실제 baseline을 확인하고 자기 기록과 격리된 작업 공간에서 후보를 검증한다.
3. PoC 담당자는 겹치지 않는 작업을 계속한다. 계약·파일 충돌에 의존하는 부분만 조율한다.
4. 후보 delta와 증거를 전달받아 현재 코드의 변경을 확인하고 통합한다.
5. 합친 코드에서 PoC 실제 흐름과 관련 기능·성능을 재검증한다.

`.gsp-work`는 기록이며 알림·코드 동기화·독점 잠금 기능이 아니다. 워커의 후보 완료는 통합 완료와 다르다. 문서 및 설치 검사 통과는 실제 사용자 PoC 성능 개선이나 자동 협업을 입증하지 않는다. 이 저장소의 변경이 다른 프로젝트나 이미 실행 중인 세션에 자동으로 적용되지는 않는다.
