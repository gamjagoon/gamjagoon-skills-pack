# 개발 전 단계의 변경 대응 검토

- 단계: Q1–Q6 합의와 R1–R9의 요구/설계/Task/개발 리뷰 완료. 실제 구현과 검증 결과는 [Task 문서](tasks.md)에 기록했다.
- 요청 범위: 기존 GSP 전체 단계의 변경 처리, 개정 기반 DAG 검사, 같은 VM/계정에서 선택형 B 조정 기능 구현·검증·설치 구성 반영. 대상 VM 배포나 실제 사용자 세션 제어는 포함하지 않는다.
- 현재 결과: 공통 변경 절차, 선택형 DAG v2의 현재 기준 검사, 같은 VM/계정의 B 조정 도구를 구현했다. 실제 대상 VM과 모델 worker 행동은 별도 검증 대상이다.
- 변경: 합의 후 구현·설치 구성을 반영했다. 과거 이력과 기존 dirty 변경을 보존했다.

## 원문과 기존 합의

> 모든 개발 과정에서 유연하게 대처 가능한 구조를 넣기 위한 방법에 대해서 생각해봐 모르는건 나에게 물어봐

이전 대화에서는 개발 도중 요구사항·아키텍처 변경 가능성, 기존 Task에 새 작업 추가, 독립 세션/agent의 병렬 협업과 DAG 검사·라우팅이 논의되었다. Markdown 문서·기존 ID·완료 이력·다른 작업자의 변경을 보존한다. 기존 승인 범위의 작업은 반복 승인 없이 진행하고, 실제로 필요한 의도·범위·정책 결정만 질문한다.

정본은 요구사항·아키텍처·Task 문서다. `.gsp-work`는 세션별 조정 기록이며 자동 알림·동기화·파일 잠금이 아니다. 현재 Python 도구는 명시한 Task DAG와 상태·충돌을 검사하며 작업을 실행하지 않는다.

| R7 | 일반 사용자 VM에서의 적용성 | 사용자는 할당받은 VM의 일반 사용자 권한으로 개발하며 추가 프로그램 설치 없이 사용 가능한지 질문했다. 이미 제공된 Codex·Python만 사용하는 경로와 필요한 프로세스/파일 접근 조건을 제시한다. 현재 조사 환경을 대상 VM의 설치·동작 증거로 삼지 않는다. |

## 사용자 결정

Q1/Q2는 사용자 “추천으로 둘 다 해줘”, Q3/Q4는 “Q3:추천, Q4:A”로 추천안/A를 확정했다. Q5 답변은 “B 기능을 넣게 하고 싶은데 어떻게 할까? 해당 방법을 사용하면 비용이 많이 든다면 A 로 진행하고”다. B의 지원 범위와 비용은 조사 근거로 구체화하며, 추천안을 답변으로 취급하지 않는다.

| ID | 질문 | 추천 | 대안 | 상태 |
| --- | --- | --- | --- | --- |
| Q1 | 변경으로 진행 중인 작업의 전제가 달라지면 어떻게 할 것인가? | 영향받은 작업만 결과를 보존하고 안전한 지점에서 보류한 뒤 재계획 | 기존 기준의 격리 작업을 끝내고 유효한 부분만 나중에 반영 | 추천안 확정 — 사용자 “추천으로 둘 다 해줘” |
| Q2 | 새 요청에 우선순위가 없으면 어떻게 배치할 것인가? | 진행 중인 작업 유지, 새 작업을 같은 우선순위로 넣어 재계산 | 새 요청을 우선하고 필요 시 기존 작업 보류·재배치 | 추천안 확정 — 사용자 “추천으로 둘 다 해줘” |
| Q3 | 완료한 Task의 기준이 바뀌면 이력과 재작업을 어떻게 표시할 것인가? | 기존 done/PASS 보존, 새 수정·재검증 Task를 연결 | 같은 Task를 재개하고 실행 회차별 이력을 별도 보존 | 추천안 확정 — 사용자 “Q3:추천, Q4:A” |
| Q4 | 목표 구조에서 도구가 어느 수준까지 검사·제한할 것인가? | 의미 판단은 agent, 선언된 개정·참조 불일치와 미검증 기준은 Python이 검사하고 해당 새 배정 제한 | 지침·경고 중심으로 두고 배정 여부는 agent가 판단 | A 확정 — 사용자 “Q3:추천, Q4:A” |
| Q5 | 여러 독립 세션 사이에서 변경 통보·보류를 어느 수준까지 보장할 것인가? | A의 경계 확인을 공통 기반으로 유지하며, 지원되는 Codex 세션에 한정해 B의 알림·보류 요청·응답 추적 추가 | A만 적용하거나, 임의의 독립 프로세스·여러 도구까지 연결하는 B로 확대 | 사용자 B 선호, 비용이 크면 A. 조건부 결정이며 실제 동작/비용 미검증 |
| Q6 | B의 첫 지원 범위를 어디까지로 할 것인가? | 같은 VM·같은 사용자 계정의 공유 Codex app-server에 연결하고 프로젝트에 명시적으로 등록한 세션만 지원. 나머지는 A 적용 | 세션 연결 방식 변경 없이 A만 적용 | 확정 — 사용자 “그럼 그 조건으로 해줘”. 지원 범위는 같은 VM/계정·기존 Codex/Python. 대상 VM의 실제 설치/권한은 아직 미검증 |

## 범위와 다음 단계

이번 요청은 이전 설계 인터뷰의 연속이다. Q1–Q6 합의를 유지하고 구현까지 진행한다. 기한·수치 성능 목표·추가 지출 한도는 지정되지 않았다. 현재 승인된 로컬 자원에서 제한된 실험과 테스트만 수행하며 새 유료 서비스·자동 모델 turn·환경 설치를 추가하지 않는다. 과거 대안과 조사 근거는 [설계 제안](architecture-options.md)에 보존한다.

## 확정 구현 계약

원문 근거: 최초 변경 대응 요청, Q1/Q2 “추천으로 둘 다 해줘”, Q3/Q4 “Q3:추천, Q4:A”, Q5 비용 조건부 B 선호, VM/일반 사용자/무설치 질문, 최종 “그럼 그 조건으로 해줘”. 이 최종 응답은 조건부 B 지원 범위와 구현 진행에 대한 합의 확인이다. 같은 뜻의 승인 질문은 반복하지 않는다.

| ID | 구현 결과와 검증 기준 |
| --- | --- |
| R1 | 기존 8단계·adopt·reviewer에서 공통 변경 절차를 연결한다. 새 요구/설계/테스트 실패/취소/소유권 변경 사례에서 최초 영향 단계·관련 ID·후속 검증이 기록되는지 문서 및 독립 시나리오 리뷰로 확인한다. |
| R2 | 영향받는 running 작업에만 안전 지점 보류를 요청하고 독립 pending 작업은 배정 가능하다. 신규 작업은 진행 작업을 빼앗지 않고 같은 우선순위의 DAG 정책으로 추가된다. 무응답·연결 실패는 완료/보류 성공으로 취급하지 않는다. |
| R3 | 기존 done/PASS와 당시 기준을 유지한다. 새 수정/재검증 Task가 현재 수용 기준을 충족해야 완료다. 테스트에서 과거 done 유지, 이전 근거의 현재 수용 거부, 후속 재검증 후 현재 수용을 각각 확인한다. |
| R4 | 하나의 통합 담당자와 공유 루트, 명시적으로 등록한 세션, 현재 계획/계약 기준을 사용한다. 오래된 후보·동시 갱신·재시작·중복 통보를 탐지하고, 과거 기준 ACK로 최신 변경을 종결하지 않는다. |
| R5 | 의미/영향 판정은 agent가 선언하고 Python은 개정·참조·DAG·배정·현재 수용 상태를 검사한다. 기존 v1 동작을 보존하며 선택형 v2에서 stale/hold 작업과 관련 소비자의 새 배정을 제외한다. invalid 입력은 실패하고 배정하지 않는다. |
| R6 | A의 시작/단계/통합 확인을 기본으로 유지하고 B를 선택 실행한다. 감시·재전송은 모델 없이 처리한다. 등록되지 않은 세션, idle 세션의 자동 모델 실행, 무한 재시도, 강제 interrupt, 새 유료 서비스는 포함하지 않는다. idle 통지는 기록에서 다음 경계에 수령하고, active 세션에만 보류 지시를 전달한다. |
| R7 | Linux VM의 같은 계정·기존 Python 3.9+ 및 호환 Codex로 실행한다. sudo/패키지 설치/시스템 서비스/외부 포트는 필수 조건이 아니다. 도구·접근 권한·연결이 부족하면 A 모드/실패 이유를 명시하고 기록과 미해결 보류를 보존한다. |
| R8 | B는 명시적인 변경 게시, 대상 세션 전달, 전달/읽음/보류/적용·검증 구분, 지속 기록과 재시작 복구, 제한된 재시도, 상태 조회를 제공한다. ACK에는 변경 ID·정확한 개정·근거를 연결한다. 전송 성공은 업무 ACK와 다르다. 같은 계정의 협력 도구이며 악성 프로세스에 대한 격리 보장은 아니다. |

기본 사용자/문제: 여러 세션으로 기존 PoC와 최적화를 병렬 수행하는 개발자가 요구·인터페이스 변경 뒤 오래된 결과를 통합하거나 불필요한 전체 재작업을 하는 문제를 줄인다. 기존 기준은 지침/수동 기록과 v1 DAG 검사이며, 새 결과는 개정별 배정·수용 검사와 선택형 통보다. 성능 향상 수치나 자동 의미 추론은 목표가 아니다.
